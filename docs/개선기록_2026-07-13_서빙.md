# JobFit 서빙 계층 추가와 검증 기록 (2026-07-13)

FastAPI 기반 API 서버(10_api.py)를 추가하고, Swagger UI에서 실제 요청으로 검증한 기록.

## 작업 요약

**문제**
JobFit은 Streamlit 화면으로만 사용할 수 있었다. 화면은 사람용 인터페이스라서
다른 프로그램(웹 서비스, 배치 작업 등)이 검색과 분석 기능을 호출할 방법이 없었다.

**해결**
FastAPI로 JSON 창구 3개를 열었다.

| 엔드포인트 | 역할 | 비고 |
|---|---|---|
| GET /health | 서버 상태와 공고 수 확인 | 배포 환경의 생존 확인용 |
| POST /search | 이력서 기반 유사 공고 검색 | LLM 미사용 |
| POST /analyze | 검색 + LLM 적합도 분석 | Streamlit과 같은 근거 규칙 적용 |

- 벡터 저장소는 서버 시작 시 1회만 구축해 전역으로 재사용
- 요청 형식은 Pydantic으로 검증 (필수 필드, k는 1~10 범위 강제)
- Swagger UI(/docs)로 자동 문서와 수동 테스트 환경 확보

**결과 (실측)**

| 항목 | 측정값 |
|---|---|
| /search 응답 시간 | 약 0.4초 (공고 49건 기준) |
| /analyze 응답 시간 | 약 3분 (qwen3 8B, CPU 추론) |
| /search 상위 5건 | 전부 AI 직군, 신입 지원 가능 공고 우선 |

/analyze의 3분은 로컬 CPU 추론의 한계로, GPU 서빙이나 상용 API 전환이 필요한
이유를 수치로 보여준다.

## 실사용 검증에서 확인한 것 두 가지

### 1. 빈 입력을 거절한다 (우연히 확인된 안전장치)

Swagger UI 테스트 중 이력서 칸에 견본 문자열 "string"이 그대로 전송된 일이 있었다.
이때 LLM은 억지로 분석하지 않고 "이력서 내용이 제공되지 않았기 때문에 적합도
분석이 불가능합니다"라고 답했다.

프롬프트 근거 규칙(없는 경험 사용 금지, 억지 연결 금지)을 넣기 전이라면
의미 없는 입력에도 그럴듯한 분석을 지어냈을 상황이다. 규칙이 실전에서
작동한다는 증거가 됐다.

### 2. 오류의 방향이 바뀌었다: 과대평가에서 과소평가로

정상 이력서로 분석한 결과, 추천 근거는 대체로 이력서에 실재하는 내용에
기반했고 불확실한 부분은 "부분적으로 부합"처럼 표시됐다. 다만 새로운 유형의
오류가 관찰됐다.

- 이력서에 FAISS가 명시되어 있는데 "Vector Database 경험 없음"으로 판정
  (FAISS가 벡터 DB라는 도메인 지식을 연결하지 못함)
- Ollama 로컬 LLM 사용 경험을 LLM 활용 경험으로 인정하지 않음

지난 기록(2026-07-10)의 오류는 이력서에 없는 경험을 만들어내는 과대평가였다.
근거 규칙을 강화한 지금은 반대로, 있는 경험을 보수적으로 인정하지 않는
과소평가가 나타난다. 채용 추천 도구에서 두 오류의 비용은 다르다. 없는 경험을
근거로 추천하면 사용자가 잘못된 지원을 하게 되지만, 과소평가는 사용자가
근거를 보고 스스로 바로잡을 수 있다. 안전한 방향의 오류로 이동한 것이다.

**개선 방향**: 이력서를 자유 텍스트 대신 구조화된 필드(기술 스택 목록 등)로
받아 도구명 매칭을 보조하거나, 도메인 지식이 더 강한 상용 API 모드를 옵션으로
제공하는 것.
