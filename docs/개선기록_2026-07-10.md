# JobFit 검색 품질 개선 기록 (2026-07-10)

하루 동안 진행한 3차례의 개선을 문제, 해결, 결과 순으로 기록한다.

## 전체 요약

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 데이터 | 가상 공고 3건 | 실제 공고 49건 (출처 URL 포함) |
| 검색 품질 측정 | 불가능 (평가 체계 없음) | 평가셋 10문항, hit@1 / hit@3 측정 |
| 검색 정확도 (hit@1) | 측정 후 40% | 90% |
| 실사용 추천 결과 | 무관한 직군 추천 + 근거 조작 | 프로필에 맞는 신입 AI 공고 추천 |

---

## 1차 개선: 실제 데이터와 평가 체계 구축

**문제**
데이터가 직접 만든 가상 공고 3건뿐이었다. 3건 중 상위 2~3건을 반환하는 검색은
틀릴 방법이 없어서, "의미 기반 검색으로 관련 공고를 찾는다"는 주장을 검증할 수 없었다.

**해결**
- 사람인에서 실제 채용공고를 수집해 49건으로 확장 (모든 공고에 출처 URL과 수집일 기록)
- AI 엔지니어, 데이터 사이언티스트뿐 아니라 타 직군(건설, 영업, 네트워크, 하드웨어 등)을
  섞어서 검색이 골라내야 할 방해물을 만들었다
- 함정 공고 포함: AI 툴(Runway, Sora 등) 키워드가 가득하지만 직군은 영상 편집자인 공고,
  RAG와 LangChain을 요구하지만 경력 3년 이상인 공고 등
- 질문과 정답 공고를 짝지은 평가셋 10문항과 hit@1, hit@3 측정 스크립트(09_eval.py) 작성

**결과**
첫 측정에서 hit@1 40%, hit@3 50%. 검색 품질에 실제 문제가 있다는 것이
감이 아니라 수치로 드러났다.

## 2차 개선: 임베딩 모델 교체

**문제**
실패 사례를 보면 "영상 편집자 채용 공고 있어?"처럼 정답 공고에 문자 그대로
"영상 편집자"라고 적혀 있는 질문도 틀렸다. 여러 직무를 한꺼번에 뽑는 공고가
어떤 질문에든 상위로 끌려나오는 패턴도 있었다. 검색 로직이 아니라
임베딩 모델(nomic-embed-text)의 한국어 표현력이 원인이라고 진단했다.

**해결**
다국어 임베딩 모델 bge-m3로 교체하고, 같은 평가셋으로 재측정했다.
비교를 위해 평가 스크립트에 --embed-model 옵션을 추가했다.

**결과**

| 임베딩 모델 | hit@1 | hit@3 |
|---|---|---|
| nomic-embed-text | 40% | 50% |
| bge-m3 (채택) | 90% | 100% |

이후 데이터를 33건에서 49건으로 늘려(방해물 16건 추가) 재측정해도
90% / 100%가 유지됐다. 함정 문항(영상 편집자 vs AI 개발, 경력직 구분)도 통과했다.

## 3차 개선: 실사용에서 발견한 검색 쿼리 설계 결함

**문제**
평가 점수는 90%인데, 실제 앱에 이력서를 넣고 "내 이력서에 맞는 공고 추천해줘"를
실행하자 무관한 직군(마케팅, 매장 정보보안)이 추천됐다. 원인을 추적한 결과:

1. 앱의 검색이 이력서가 아니라 질문 문장만으로 이루어지고 있었다.
   "내 이력서에 맞는 공고 추천해줘"라는 문장에는 직무 정보가 전혀 없어서,
   검색은 아무 질문에나 걸리는 범용 공고를 반환했다.
2. LLM은 잘못 검색된 공고를 받아도 거부하지 않고, 이력서에 없는 경험까지
   만들어가며 적합한 것처럼 정당화했다.
3. 평가셋의 질문은 내용이 있는 질문("영상 편집자 공고 있어?")이라
   이 경로의 결함이 평가에 잡히지 않았다. 벤치마크와 실사용의 경로가 달랐던 것이다.

**해결**
- 검색 쿼리를 질문 단독에서 질문+이력서 본문으로 변경 (이력서가 검색의 핵심 신호)
- 검색 결과 수를 k=2에서 k=5로 늘려 LLM이 비교할 후보를 확보
- 프롬프트에 근거 규칙 추가: 제공된 공고 중에서만 추천, 공고 번호와 회사명 인용,
  이력서에 없는 경험 사용 금지, 경력 요건 불일치 명시, 적합한 공고가 없으면 없다고 답변

**결과**
같은 이력서로 재실행하자 상위 5건이 전부 AI 직군 공고(대부분 신입 가능)로 바뀌었고,
경력 요건이나 기술 스택이 맞지 않는 공고는 이유와 함께 "적합하지 않음"으로 분리됐다.

## 남은 한계와 다음 단계

- 소형 로컬 LLM(qwen3 8B)의 잔여 환각: 프롬프트 규칙으로 크게 줄었지만,
  공고의 요구사항(Hugging Face, 인턴십 등)을 보고 이력서에 없는 경험을
  근거로 드는 사례가 남아 있다. 추천 근거의 인용 검증 단계 추가 또는
  상용 API 모드 옵션이 다음 개선 방향.
- FastAPI 서빙과 Docker 컨테이너화, 클라우드 데모 배포 (예정)
- 워크넷 오픈API 연동으로 공고 수집 자동화 (API 승인 대기)

## 이번 개선에서 배운 것

- 평가셋이 없으면 검색 품질은 주장일 뿐이다. 측정이 있어야 개선이 있다.
- RAG의 품질은 LLM이 아니라 검색이 결정한다. 검색이 틀리면 LLM은
  틀린 결과를 그럴듯하게 포장할 뿐이다.
- 벤치마크 점수와 실사용 품질은 다를 수 있다. 평가가 실제 사용 경로를
  지나가는지 확인해야 한다.
- 직접 써보는 것(dogfooding)이 가장 빠른 버그 발견 방법이었다.
